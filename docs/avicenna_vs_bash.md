# AVICENNA vs. the original bash pipeline — functional differences

**Purpose.** AVICENNA is a Python/PHIL reimplementation of the original bash
crystallography pipeline (the original bash scripts). The guiding
principle is that **AVICENNA's defaults reproduce the bash pipeline's behavior**,
so the bash workflow remains the de-facto default. Deliberate, justified
divergences are allowed — this document tracks every *functional* difference so
the changes are explicit.

**Scope.** Only **functional** differences (behavior, parameters, control flow,
thresholds, added/removed steps). Pure implementation details (Python vs bash,
PHIL config, logging format, code structure) are out of scope except where they
change behavior.

**Maintenance.** Update this file in the same change that introduces a behavioral
difference. Keep entries tagged and dated. When in doubt, note the bash baseline
with a `file:line` citation.

**Legend**
- `[parity]` — intentionally matches the bash (may be re-expressed/renamed)
- `[change]` — justified divergence from bash defaults
- `[added]` — capability with no bash equivalent
- `[removed]` — bash capability deliberately dropped
- `[gap?]` — bash capability whose AVICENNA status is unverified (TODO)

_Last updated: 2026-10-01._

> **Note (2026-07-02):** the `--legacy` and `--bash` execution paths (running the
> original bash scripts / the pre-PHIL hard-coded Python runners) have been
> removed. AVICENNA is now PHIL-only. This document remains the design record of
> how the PHIL pipeline's *defaults* reproduce the bash pipeline's behavior; the
> bash scripts themselves are the historical baseline in the left columns below.

## 1. Processing sub-pipeline (`vic.process`)

Bash baseline: `xds_pipeline_single.sh` / `xds_pipeline_prep.sh` orchestrating
`run_xds.sh`, `run_pointless.sh`, `run_aimless.sh`, `run_rfree.sh`,
`run_xdsconv.sh`, `run_xtriage.sh`. Core loop: XDS → Pointless → Aimless (no
cut) → XDS → Pointless → Aimless (res cut) → [improve?] XDS → Pointless →
Aimless → R-free/ctruncate → Xtriage. AVICENNA default sequence
(`default_processing.phil`): `1_xds → 2_pointless → 3_aimless → 4_xds →
5_pointless → 6_aimless → 7_xds → 8_pointless → 9_aimless → 10_rfree →
11_xtriage`.

| P18 | Pre-scan (raster / snapshot) rejection | CBF-oriented; no concept of a pre-scan. | P20 | Per-dataset run record (`info.json`) and the completion signal | None. It carries the outcome (`running` / `completed` / `failed`), the failing step as its own field, per-step status and timing, what the job knew without parsing (image range, resolved processor count, known space group, forced or not), and the Aimless statistics, parsed once at the step that produced them, with each resolution shell kept whole. **Sentinel side:** the completion sentinel gathers every record into the project's `info.json`, keyed by dataset tag and merged into the record written at start-up, so the crystal-list identity is never overwritten. | P21 | Re-running into a used project folder | Every dataset folder that already exists is deleted and processed again (`image_range.sh:26`); there is no notion of an earlier run | Before anything is written, the run compares the output folder with its input and puts every dataset in one class: **done** (rejected before submission, or every job it ran left a record with a final outcome), **frayed** (started but not finished: a job with no record, a record still `running` or unreadable, or a failure whose forced retry did not finish) or **untouched**. **No earlier run:** go ahead. **Incomplete:** refuse with exit 3 and give the counts. **Complete:** refuse with exit 4. A refusal writes nothing. `--resume` completes an incomplete run: each frayed dataset's folder is deleted (it stopped for reasons unrelated to its data) and only frayed and untouched datasets are submitted. The two flags are mutually exclusive (exit 2). Resume is opt-in because resuming by default after a settings change would leave datasets processed with different settings. **Exit statuses**, shared by `vic.process`, `vic.refine` and `vic.analysis`: 0 success, 1 failure, 2 usage error, 3 incomplete run found, 4 complete run found, 5 another run's jobs still alive (P19). | `[change]` (opt-in resume; bash always redid) |
| P22 | Result quality filter and selection | No automatic selection. `xds_check.sh` prints a report (`all` rows, or `top` per pin) and no script writes `qrefine_list.txt`, so what goes forward to refinement is chosen by hand. `top` is described as the highest-ISa job in the README and as the highest-resolution job in the script's own comment; the code sorts ascending on the outer-shell resolution in Å and takes the last row (`xds_check.sh:147`). No quality thresholds: CC1/2 (outer shell, `xds_check.sh:69`) is reported, never compared | `ProcessingFilter` chooses automatically, one result per crystal. **Thresholds** (a result failing any is dropped): overall completeness ≥ 80 %, multiplicity ≥ 3, overall CC1/2 ≥ 0.70, outer-shell CC1/2 ≥ 0.30, overall Rpim ≤ 0.20. **Per dataset folder** (crystal forms, index ranges, forced retries): lowest overall Rpim wins, ties broken by higher overall CC1/2, then higher resolution. **Per physical crystal**: the same comparison keeps one of the dataset folders a re-mounted pin produces. Every loser is recorded in `info.json` as failed with its reason, including `superseded by <winner tag>` (P20). The thresholds are fixed in code, not yet options. `vic.process --no_filter` skips the filter for `qrefine_list.txt` only, for testing. | `[added]` (automatic selection) |

## 2. Refinement sub-pipeline (`vic.refine`)

Bash baseline: `qrefine.sh` (per dataset × water suffix): input prep → rigid-body
`phenix.refine` (5 macro-cycles, `hydrogens.refine=riding`) → [if Rfree >
`mr_cutoff`] `phenix.phaser` → jelly `refmac5` (4 cyc, ridge σ 0.01) → restrained
`refmac5` (8 cyc) → [if `mr_try_monomer` and (phaser failed or final Rfree > 0.4)]
monomer phaser → jelly → restrained. Per-crystal MR parameters came from
`qrefine_input_parameters.txt`. AVICENNA default sequence
(`default_refine.phil`): `1_phaser → 2_jelly → 3_refmac5 → 4_fill`.
**Rigid body is no longer in the default sequence** — Phaser is the first step
(see R1). The `phenix.refine` step type remains available for custom pipelines.

| R15 | Which processing results are refined | Every row of `qrefine_list.txt` is refined, so every processing variant of a pin (crystal form, index range, forced retry) gets its own job, in a folder named from the list columns; `qrefine_check.sh` then reports one refinement per pin (`top`/`crystal` modes): the highest-resolution one unless its Rfree is more than 0.05 above the lowest, otherwise the lowest-Rfree one within 1 Å of the best resolution (`qrefine_check.sh:132`). The choice is printed, not acted on | One job per dataset, in `qrefine/<dataset tag>/`, refining the dataset's processing winner (P22) read from `info.json`: its merged data file is recorded as `final_mtz` by the processing job that produced it, so no path is rebuilt from folder names. Nothing is selected after refinement: the refined model is an intermediate (no ligand fitted, no ligand-induced changes modelled), so its statistics are not a basis for rejecting it, and pandda.analyse screens its own input (R-free cap, space group, RMSD to the reference, low-resolution completeness, Wilson plot). A winner whose record has no `final_mtz` is skipped with a warning. `qrefine_list.txt` is an export (P20); `vic.refine -l <list>` refines the rows of a list instead, for testing, and refuses a list that names one dataset twice. | `[change]` (selection before refinement, not after) |
| R16 | Per-dataset refinement record | None. Results are known only by scraping the job folders afterwards | Every refinement job keeps `<dataset tag>_info.json` in its job folder, rewritten after every step as in P20, carrying the dataset tag as a field, the input MTZ, the outcome and failing step, and on success Rwork, Rfree and resolution from `final_refined.pdb` plus the paths of the canonical output (R9b). The refinement sentinel gathers the records of the datasets the run was given into `info.json`, matching them by the tag they carry rather than by folder name: status `refined`, or `failed` with the reason (the failing step and error, where a killed job stopped, a job that left no record, or no job at all). Refinement's fields are stored under their own names (`refine_outcome`, `refine_job_dir`, `refine_failed_step`, `refine_resolution`, `rwork`, `rfree`, `final_refined_pdb`, `final_refined_mtz`) so the processing winner's fields are kept. A failure also sets `failed_stage = refine`, and such a dataset is still refinement input, so it is refined again by the next run. | `[added]` |
